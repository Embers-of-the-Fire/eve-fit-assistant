## What I do

- Locate the existing changelog entry under `docs/changelog/` for a given version code (e.g. `0.3.0`).
- Read the raw `changelog.md` (git-cliff output, also provided by the user) as source material.
- Author curated, user-facing release notes in `content.en.md` and `content.zh.md`.

## When to use me

Use this when the user asks to write a changelog or release notes for a version and provides git-cliff output as the source material. Do NOT run `./x release relnote` or `git-cliff` yourself.

## Preconditions

`./x release relnote` is expected to have already run, so the entry directory already contains `spec.yaml` and `changelog.md`. Do NOT create or overwrite those two files.

- If the directory or `changelog.md` is missing, tell the user to run `./x release relnote` first (or confirm before creating the entry yourself).
- If `content.en.md` / `content.zh.md` already exist, do NOT overwrite them silently; ask first.
- The user-provided git-cliff output should match `changelog.md`; if they differ, trust the file on disk and mention the discrepancy.

## Inputs

- **Version code** (required): semver like `0.3.0` or `0.2.0-beta.1`. If the user did not state one, ask.
- **git-cliff output** (required): the raw markdown produced by git-cliff. If missing, read `<entry>/changelog.md` instead.

## Entry layout

For version `0.3.0`, the entry is `docs/changelog/0-3-0/` (dots replaced with hyphens; pre-release `0.2.0-beta.1` → `0-2-0-beta-1`):

| File | Origin |
|------|--------|
| `spec.yaml` | Already generated by `./x release relnote` — do not touch |
| `changelog.md` | Already generated by `./x release relnote` (git-cliff, `--strip header`) — do not touch |
| `content.en.md` | **You author this** — curated English release notes |
| `content.zh.md` | **You author this** — curated Chinese release notes, same structure |

## Writing the curated content files

Derive both content files from the git-cliff output, but rewrite for end users:

1. Start with `# v<version> Release Notes` and a one-sentence intro (e.g. "This release includes the changes listed below.").
2. Group changes into a small number of **themed sections** (e.g. `## Implants`, `## Market Pricing`), not git-cliff's commit categories. Drop pure chores, refactors, and CI/build changes that users cannot observe.
3. Each bullet describes the **user-visible effect**, not the commit message. Omit PR numbers and scope prefixes like `**fit:**`.
4. Keep it concise: one bullet per feature or fix, plain language.
5. Write `content.zh.md` as a faithful Chinese translation with the same structure; the Chinese title uses `发布说明` (e.g. `# v0.4.0 发布说明`).

Style reference: `docs/changelog/0-4-0/content.en.md` and `docs/changelog/0-4-0/content.zh.md`.

## Validation

- Confirm `spec.yaml` and `changelog.md` were left untouched.
- Confirm both content files exist, share the same section structure, and cover every user-visible change from the git-cliff output.
