## What I do

- Locate the existing changelog entry under `docs/changelog/` for a given version code (e.g. `0.3.0`).
- Research what actually shipped (git-cliff output, plus diffs/PRs/docs when messages are unclear).
- Author curated, end-user-facing release notes in `content.en.md` and `content.zh.md`.

## When to use me

Use this when the user asks to write a changelog or release notes for a version. Do NOT run
`./x release relnote` or `git-cliff` yourself.

## Preconditions

`./x release relnote` is expected to have already run, so the entry directory already contains
`spec.yaml` and `changelog.md`. Do NOT create or overwrite those two files.

- If the directory or `changelog.md` is missing, tell the user to run `./x release relnote` first.
- If `content.en.md` / `content.zh.md` already exist, do NOT overwrite them silently; ask first.
- If the user pastes git-cliff output that differs from `changelog.md` on disk, trust the file
  and mention the discrepancy.

## Inputs

- **Version code** (required): semver like `0.3.0` or `0.2.0-beta.1`. If the user did not state one, ask.
- **git-cliff output**: read `<entry>/changelog.md`; user-pasted output is only a convenience copy.

## Entry layout

For version `0.3.0`, the entry is `docs/changelog/0-3-0/` (dots → hyphens;
`0.2.0-beta.1` → `0-2-0-beta-1`):

| File | Origin |
|------|--------|
| `spec.yaml` | Generated by `./x release relnote` — do not touch |
| `changelog.md` | Generated by `./x release relnote` (raw git-cliff) — do not touch |
| `image.png` | Generated by `./x release version-image` — do not touch |
| `content.en.md` | **You author this** |
| `content.zh.md` | **You author this** |

## How these files are consumed (machine contract — read first)

The content files are machine-parsed and rebroadcast; violating this contract breaks releases:

- `bootstrap/docs/document_parser.py` extracts the **H1 as the announcement title** and the
  **first plain paragraph after it as the summary** shown in announcement lists. The parser
  fails if there is no plain (non-heading, non-list, non-code) paragraph.
- The body shown to users is `content body + "## Changelog" / "## Full Changelog" + the raw
  changelog.md`, appended automatically (`bundled_docs.py`, `release_github.py`). Therefore
  content files must NOT contain their own "Changelog"/"Full Changelog" section or raw commit list.
- `content.zh.md` is posted to QQ groups with the H1 stripped (`notify-qqbot` in
  `.github/workflows/_release.yml`), so the zh body must read standalone, without its heading.

## Source material

`changelog.md` is the coverage checklist, not the text. Commit messages are written for
developers; when one does not clearly state what the user sees, read the diff, the PR, or the
relevant docs/manual before writing the bullet. Never invent behavior you cannot confirm.

## Writing the content files

### Structure (both locales, identical)

```markdown
# v<version> Release Notes          /  # v<version> 发布说明

<1–2 sentence summary naming the headline changes.>

## <Theme>

- bullet
- bullet

## Fixes                            /  ## 修复

- bullet
```

- **Summary paragraph**: 1–2 sentences naming the 1–3 most important changes in plain language.
  It is extracted and shown on its own — never write filler like
  "This release includes the changes listed below." (`0-2-0/content.en.md` is the good example.)
- **Sections**: 2–5 themed sections ordered by user impact, then a final `## Fixes` / `## 修复`
  if any fixes remain. Omit empty sections. Do not use git-cliff categories
  (Added/Fixed/refactor/Chore/Dependencies/Documentation) as section names.
- **Coverage**: every user-visible change in `changelog.md` appears exactly once. Drop chores,
  refactors, CI/build, docs, and dependency bumps with no observable effect.

### Bullets

- One bullet per user-perceivable capability or symptom. Collapse commits that are steps of the
  same feature into one bullet; split one commit into two bullets only if it ships two
  independent user-visible things.
- Describe the outcome, not the mechanism. Start with a present-tense verb: "Show…", "Add…",
  "Fix…". Fixes describe the symptom the user had: "Fix icons not loading after app data
  storage relocation", not "rebuild stale native dir".
- Plain language. No PR numbers, scope prefixes (`**fit:**`), package names
  (`efa-fit-snapshot-ts`), or infra jargon (D1, Worker, edge caching, FTS5, "content-addressed",
  "500-proof") — translate to what the user gets ("faster page loads", "search the manual").
- Use the game's own terminology in both locales (fit/装配, implant/植入体, warp/跃迁, …).
- Keep the whole file scannable: roughly one screen; merge or drop rather than enumerate.

### Chinese file (`content.zh.md`)

- Same sections and bullet count as the English file, same order.
- Translate for Chinese players, not word-by-word; use the official EVE Chinese localization
  for in-game terms.
- Keep version numbers, URLs, product names, and code identifiers unchanged.

### Worked example

Raw commits:

```
- **platform:** version-keyed edge caching for all anonymous HTML pages (#383)
- **platform:** add registered fit links addressed by fit hash (#386)
- **charge:** window the charge count by 1e-4 (#371)
```

Curated bullets:

```
- Shared fit pages load faster
- Fix charge counts sometimes being slightly off
```

## Validation

Machine contract:

- Each content file has exactly one H1: `# v<version> Release Notes` / `# v<version> 发布说明`.
- The paragraph right after the H1 is a plain paragraph (no heading/list/code) and is informative.
- Neither content file contains a "Changelog" / "Full Changelog" section or raw commit lines.
- en/zh have identical section headings (translated), order, and bullet counts.
- `spec.yaml` and `changelog.md` untouched.
- Optionally verify parsing:
  `uv run python -c "from bootstrap.docs.document_parser import parse_locale_document; parse_locale_document(p, 'en')"`
  for each content file.

Quality (read the result as a player who has never seen this repo):

- Could each bullet be understood without knowing the codebase? Any internal jargon left?
- Does the summary alone tell a user why they should care about this update?
- Is every user-visible commit in `changelog.md` covered exactly once?
