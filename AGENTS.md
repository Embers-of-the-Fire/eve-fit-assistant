# AGENTS.md

This repository is a multi-language workspace for EVE Fit Assistant.
Agents should read this file before editing code.

## Scope

- Stack: Flutter/Dart frontend, Rust backend via `flutter_rust_bridge`, Python tooling/data generation.
- Primary entrypoints: `lib/`, `rust/`, `data/`, and the workspace manager `x.py`.
- Prefer repository workflows over ad hoc commands; `./x` is the canonical helper.
- There is no repo-local `.cursorrules`, `.cursor/rules/`, or `.github/copilot-instructions.md` at the time of writing.

## Environment Setup

- This repo targets Nix development shells; start with `nix develop` when possible.
- Tooling provided by `flake.nix`: Flutter, JDK 17, `uv`, Python 3, Rust/Cargo, `rustfmt`, `clippy`, `protoc`, `flutter_rust_bridge_codegen`.
- Do not use `apt`, `brew`, `npm`, or `nix-env` in this repo.
- Initialize dependencies with:
- `flutter pub get`
- `uv sync`
- Android local properties are generated by the dev shell; avoid editing `android/local.properties` manually unless required.

## Required Local Config

- Before Rust codegen, linting, or backend tests, make sure the backend `.env` exists under `rust/lib/eve-fit-os/.env`.
- The repo README recommends a local datasource such as `tranquility` for development.
- `efa.config.toml` is version-controlled; treat datasource/workspace changes there as intentional project changes.
- Data build commands require a selected workspace:
- `./x workspace list`
- `./x workspace default <workspace>`

## High-Value Commands

## Dependency / workspace bootstrap

- `nix develop` - enter the preferred dev shell.
- `flutter pub get` - install Flutter/Dart dependencies.
- `uv sync` - install Python dependencies.
- `./x workspace list` - inspect configured data workspaces.
- `./x workspace default <workspace>` - set the default data workspace.

## Build commands

- `flutter build apk` - build the Android app.
- `cargo build -p rust_lib_eve_fit_assistant` - build the FRB Rust bridge crate.
- `cargo build -p eve-fit-os` - build the backend engine directly.
- `./x build data` - generate the selected workspace bundle.
- `./x build data --no-hash` - faster dev-only data build without snapshot manifest updates.
- `./x build increment <baseline_manifest>` - create an incremental patch bundle from a baseline manifest.

## Code generation commands

- `./x generate all -f` - run all code generation and then formatting.
- `./x generate protobuf` - regenerate Python and Dart protobuf outputs.
- `./x generate rust` - regenerate Flutter Rust Bridge glue.
- `./x generate dart` - run Dart `build_runner` codegen.
- `./x generate dart --watch` - watch mode for Dart codegen.
- `./x generate l10n` - regenerate localization files.

## Lint / format commands

- `./x lint` - canonical full-project fix/lint/format pass.
- `./x format` - formatting only; equivalent to `./x lint --no-check`.
- `uv run ruff check --fix` - Python lint autofixes.
- `uv run ruff format` - Python formatting.
- `dart analyze` - Dart static analysis.
- `dart fix --apply` - apply available Dart fixes.
- `dart format lib/` - format Dart source under `lib/`.
- `cargo fmt --package rust_lib_eve_fit_assistant` - format the main Rust bridge crate.
- `cargo clippy --fix --allow-dirty --package rust_lib_eve_fit_assistant` - lint/fix the main Rust bridge crate.

## Test commands

- There is currently no top-level Flutter `test/` directory in this repo.
- The active automated tests are Rust integration tests under `rust/lib/eve-fit-os/tests/`.
- `cargo test -p eve-fit-os` - run all backend tests.
- `cargo test -p rust_lib_eve_fit_assistant` - run tests for the bridge crate workspace member.
- `cargo test -p eve-fit-os --test test_basic_fit -- --nocapture` - run one integration test file.
- `cargo test -p eve-fit-os test_basic_fit -- --exact --nocapture` - run one specific test function.
- If Flutter tests are added later, use `flutter test test/path/to/file_test.dart` for a single file.

## Validation Expectations

- After changing code, run the relevant formatter and linter for the touched language(s).
- Minimum expected validation for mixed-language work is usually `./x lint`.
- For Rust logic changes, also run targeted `cargo test` commands.
- For data generation changes, rerun the specific generator plus any affected Rust tests.
- For localization changes, run `./x generate l10n`.
- For codegen-affecting Dart changes, run `./x generate dart`.

## Files Agents Should Usually Not Edit Manually

- Generated Dart files: `*.g.dart`, `*.freezed.dart`, protobuf outputs under `lib/data/proto/`.
- Generated Rust bridge file: `rust/src/frb_generated.rs`.
- Generated native Dart bridge outputs under `lib/native/`.
- Build artifacts under `build/`, `target/`, and generated bundle outputs unless the task is explicitly about them.
- Lockfiles may reflect mirror-specific environments; update them only when the task genuinely requires dependency changes.

## Architecture Notes

- Flutter UI and app state live under `lib/`.
- Rust bridge code lives under `rust/`; the heavy calculation engine is the nested crate `rust/lib/eve-fit-os`.
- Python under `data/` and `x.py` handles workspace management, codegen helpers, and bundle generation.
- The app depends on generated data, generated localization files, protobuf outputs, and FRB glue.

## Dart Style

- Follow `analysis_options.yaml`; analyzer is strict: `strict-casts`, `strict-inference`, and `strict-raw-types` are enabled.
- Use package imports only; `always_use_package_imports` and `avoid_relative_lib_imports` are enforced.
- Import order follows existing files: `dart:` imports first, blank line, then `package:` imports, sorted consistently.
- Use double quotes in Dart source.
- Formatter width is 100 columns.
- Public APIs should have explicit types; `type_annotate_public_apis` is enabled.
- Prefer `final` locals, `const` constructors/literals, expression bodies where they stay readable, and named constants.
- Avoid `dynamic`, positional booleans, redundant defaults, and unnecessary nullable plumbing.
- Prefer small immutable state models with `freezed` unions and `copyWith` updates.
- Riverpod patterns in this repo use provider names ending in `Provider` and notifier/service classes with descriptive nouns like `Fit`, `FitEmulatorService`, `AppSettingService`.
- Keep widget classes `UpperCamelCase`; private helpers use leading underscores.
- File and directory names use `snake_case`.
- When impossible states are hit, log context and throw a typed error such as `StateError` rather than failing silently.
- Use `unawaited(...)` deliberately for deferred async work and keep state mutation out of widget build timing hazards.

## Localization Style

- `l10n/app_zh.arb` is the `template-arb-file`; define typed placeholder `@...` metadata there.
- Other ARBs such as `l10n/app_en.arb` should contain translation values only, not placeholder metadata blocks.
- After localization changes, run `./x generate l10n` and the relevant formatter/linter.

## Rust Style

- `rustfmt.toml` sets 100-column formatting and enables field/init and `?` shorthands.
- Keep modules/functions in `snake_case`; types/traits/enums use `UpperCamelCase`; constants use `SCREAMING_SNAKE_CASE`.
- Prefer `anyhow::Result<T>` at fallible API boundaries and propagate with `?`.
- Keep FRB-facing APIs small and explicit in `rust/src/api/`.
- Put core fitting logic in `rust/lib/eve-fit-os` rather than the bridge crate when possible.
- Use `unwrap`/`expect` sparingly in production code; they appear more often in tests than in core APIs.
- Prefer borrowing over cloning when practical, and keep data transformations explicit.
- Run targeted tests after touching calculation passes, fit models, protobuf loading, or server APIs.

## Python Style

- Python requires 3.13+ and uses `uv`, not a global virtualenv workflow.
- Ruff is the formatter and linter; line length is 100, indentation is 4 spaces, and double quotes are preferred.
- `from __future__ import annotations` is required by Ruff isort settings.
- Keep imports one per line, grouped cleanly, and move type-only imports behind `if TYPE_CHECKING:` when appropriate.
- Relative imports are banned; use absolute imports from `data...`.
- Use `snake_case` for functions/modules, `UpperCamelCase` for classes, and preserve external schema field names when modeling upstream data.
- Pydantic models are common for validation; prefer validating external data at boundaries.
- Catch broad exceptions only around validation or I/O boundaries where you can add useful context.
- Logging helpers from `data.lib.log` are preferred over ad hoc output, though `x.py` intentionally uses Click terminal output heavily.

## Error Handling Guidelines

- Fail fast on invalid state, missing config, or corrupted generated data.
- Include enough context in logs to diagnose workspace, file path, fit ID, type ID, or bundle ID issues.
- Prefer typed errors (`StateError`, `anyhow::Result`, `ValidationError`) over stringly-typed failure paths.
- Do not swallow exceptions just to keep flows moving; either recover intentionally or bubble the failure.
- In async/stateful Dart code, update state transitions explicitly so loading/error/loaded states remain coherent.

## Agent Workflow Recommendations

- First inspect whether a task touches generated code, workspace data, or multiple languages.
- If editing source that feeds codegen, regenerate outputs instead of hand-editing generated files.
- Keep changes minimal and consistent with nearby code; this repo already has strong established patterns.
- Mention any required workspace or `.env` prerequisites when you cannot run backend generation/tests locally.

## Agent Safety and Right Rules

- You **MUST** sign-off on changes using `git commit -s` or include a `Signed-off-by`.
- You **MUST** include a `Assisted-by` tag following the format:
  `Assisted-by: [Provider]:[model] [tools]`. For example,
  `Assisted-by: Claude:claude-opus-4.6 spark fuzz`.
  Note that trivial tools **MUST** not be included, like `git`, `bash`, `apply_patch`, etc.
